# Operations

How a project runs once it ships: its environments, how a release reaches production, backups and recovery, uptime, alerting and postmortems, and the CI that runs the gates. `code-style.md` says what good code is; `quality.md` says how it is checked and how a release is cut; this file says how the running system is kept.

The words mean what they mean in `code-style.md` §0. A **Law** has an ID and is a must. It is enforced only once its gate is commissioned: a row in the gate table at the end of this file (which counts as a row of `quality.md` §2) and an entry in `settings.gates`. Until then, and wherever a Law says "review-enforced", a reviewer holds it, as with Doctrine. **Doctrine** is a should, held by review.

The tools this file names for a job are the owner's choice for that job (`constitution.md` §4, defaults named in the governance files): using one needs no one-way-door question. Its account and keys are still an owner action.

## 1. Environments

- **`L-ENV-1` two environments: a preview per PR, and production.** The host builds a preview for every PR (Vercel preview deployments, Render preview environments). There is no long-lived staging: what a staging server would show, the PR's preview shows. The `release-staging` class goes unused; a preview is run state, never a staging act. Review-enforced.
- **`L-ENV-2` a preview is never indexed.** Every response outside production carries `X-Robots-Tag: noindex, nofollow`, and its `robots.txt` disallows everything. The app decides this from its typed config (below), never from the hostname. Vercel adds the header to its own preview URLs; the app's header covers every other host and domain. Gate: a request test, run with preview config, asserts the header and the `robots.txt` (test gate).
- **`L-ENV-3` a preview has no production data and no production keys.** Its database is seeded from prod-shaped seeds (`L-TEST-5`), never a copy of production, scrubbed or not. It uses development and test keys only (`code-style.md` §10): Stripe test mode, a Resend test key, Sentry environment `preview`. Production's decryption key never reaches a preview. Gate: the config module lists the live-key prefixes of the vendors the project uses (Stripe's `sk_live_` and `rk_live_`, and any other vendor's that has one) and refuses to boot outside production with a key that matches; a unit test of the config parse proves it (test gate). A vendor whose live and test keys look alike is covered by review only. The rest is review.
- **Doctrine — the environment is one typed config key.** `app_env` is one of `development`, `test`, `preview`, `production`, parsed at boot with the rest of the config (`L-SEC-3`). Never infer it from `NODE_ENV` or `RAILS_ENV`: a preview runs those as `production`.

## 2. Releases and deploys

How a release is cut, and who may ship it, is `quality.md` §5 and the `release-production` class (`constitution.md` §1). This section fixes where production deploys from. It changes nothing about who may promote: promoting stays `release-production`, on whatever rung the owner has set, and every gate still passes at the tagged commit.

- **`L-REL-1` production deploys only from a release.** `main` is integration. A release is a tag on `main` with a GitHub Release (`quality.md` §5). Promoting it fast-forwards a `production` branch to that tag (`git push origin vX.Y.Z^{commit}:refs/heads/production`, `quality.md` §5, step 3), never a new commit on `production`. The host deploys only from `production`: Vercel's Production Branch, Render's auto-deploy branch, set to `production`, with auto-deploy from `main` off.
  - **Settings.** The project's `release` setting is `{ "branch": "production" }`. A project adopted on `"tag"` or `"merge"` (`quality.md` §5, step 3) stays as it is until it moves. `release` is the owner's setting (`quality.md` §4, `governance-edit`), so the supervisor moves a project to it with a chore PR and that question, citing this rule as the recommendation.
  - **What enforces it.** The host's branch setting and the forge's protection on `production` (only the releasers may push; no pull requests into it) are the owner's to set, as an owner action. devteam doesn't read either. Review-enforced, outside those.
- **`L-REL-2` a GitHub Release lists its PRs.** It is created with `--generate-notes --notes-start-tag <previous-tag>` beside `--notes-file` (`quality.md` §5, step 2), so the body holds the supervisor's notes and GitHub's list of the PRs merged since the previous tag. Review-enforced.
- **`L-REL-3` roll back by pointing production at the previous tag.** It is `quality.md` §5, step 4, in the class of a release (`release-production`). While an incident is open, a rollback is a remediation the owner listed (`production-remediation`, `process/supervisor.md` Monitoring), whatever rung `release-production` is on, so the owner sees it coming; where no rollback remediation is listed, ask the owner, with no default. Moving `production` back is the one force push that branch takes, so its protection allows the releasers to force-push it. Where the forge can't, revert on `main`, tag, and promote that tag. A rollback across a migration is a one-way door (`process/supervisor.md`, Remediating). Never commit a hotfix to `production`: a fix goes through `main` and a new tag. Review-enforced.
- **Doctrine — a release names itself everywhere.** Sentry's release is the tag, and a deploy probe reports the host's deploys as `deploy` events, so a fix's verification can see it shipped (`process/supervisor.md`, Verifying a fix).

## 3. Backups and recovery

- **Targets (proposed).** RPO 5 minutes, from point-in-time recovery; RTO 1 hour, from the decision to restore to the app serving again. If the host's account itself is lost, the off-site copy bounds the RPO at 24 hours. The README's Restore section (`project-docs.md`) states the targets the project holds.
- **`L-RECOV-1` point-in-time recovery is on.** Production's database runs with the host's point-in-time recovery (Render Postgres PITR, or the managed Postgres's own). The README states its window. Review-enforced.
- **`L-RECOV-2` a daily copy leaves the host.** Once a day a scheduled job (the job queue's recurring task, or the host's cron) takes `pg_dump --format=custom` of production, encrypts it with `age` to a public key whose private key is kept like a production secret (`code-style.md` §10: the owner's shell or the platform's secret store, never a key file in a checkout), and uploads it to Bunny Storage or Cloudflare R2, under a different provider from the host. Object storage the app writes to is copied to the same place, unless it already lives there. A backup holds personal data, so erasure reaches it through the PII mechanism (`L-PII-1`: under crypto-shredding, destroying a subject's key erases them in every copy). The job reports each run to a Sentry Cron Monitor, so a missed or failed day alerts. Review-enforced; Sentry catches a missed run.
- **`L-RECOV-3` a restore drill runs at least once a quarter, for real, and is recorded.** Restore the latest off-site copy, and at least every other drill a point-in-time restore too, into a throwaway database, never production. Run a check against it (row counts of the main tables against the copy's own, one known query the app depends on, the app booting against it). Time it, from start to the check passing. Then delete the throwaway database.
  - **Running it.** Prefer a scheduled GitHub Actions workflow that restores into a service-container Postgres, with the decryption key a secret of a GitHub environment limited to `main`. Where the key is only in the owner's shell, the drill is an owner action: the supervisor asks for it with the script to run.
  - **The record.** The supervisor records each drill as an observation, `observe --subject <the production database's component> --kind restore-drill --value <minutes> --unit min --detail "<what was restored, from where, the check and its result>"`, citing the run. A time over the RTO, or a failed check, is a problem and a ticket.
  - **What enforces it.** Nothing in the kit raises a missed drill yet: the supervisor checks the date of the last `restore-drill` at each retro. Review-enforced.

## 4. Uptime and alerting

- **`L-UP-1` every production surface has a URL sensor with an SLO.** One `kind: http` sensor per app the public reaches, on a health route that checks the database (Rails' `/up` only shows the app booted, so add a route that queries the database, or extend it), with an `slo` (`process/supervisor.md`, Monitoring). The SLO is the availability and p95 the design states; without one, `uptime: 0.999` and `p95_ms: 800`. Starting sensors is the supervisor's, with no question. Gate: none; `sensor discover` lists the URLs nothing watches yet.
- **`L-UP-2` Sentry alerts on exceptions.** Sentry runs on the server, in the browser and in the app, with an alert rule on each new issue and each regression, sent to the owner. A Sentry probe feeds the same exceptions to the supervisor's triage (`process/supervisor.md`, Monitoring). Review-enforced.
- **No other uptime vendor.** The two above are the whole of it. Their limit, stated so nobody assumes more: sensors poll only while the supervisor runs (`wait`), so a site that goes down while no supervisor is running raises nothing until one starts, and Sentry sees errors, not silence. A supervisor running all day on a cloud box narrows the gap. Widening it with a paging vendor is a new vendor, the owner's one-way door.

- **`L-PM-1` a big incident gets a blameless postmortem.** A big incident is an outage (a URL sensor `down` for 15 minutes or more) or lost or corrupted production data. Every other incident runs on the incident machinery alone (`process/supervisor.md`, Monitoring: triage, fix, verification). Once a big incident's fix is verified, the supervisor writes `project/postmortems/<date>-<slug>.md` in a chore of its own (`chore start postmortem-<slug>`) with four sections: **Timeline** (from the first signal to verified, from the log and the sensors), **Cause**, **Fix** (the fix ticket and the release that shipped it, the remediation act, or "recovered on its own"), and **What stops it recurring silently** (the fix ticket's reproducing test, `worker.md`, and the sensor or alert that would catch it next time; a `probe-missed` finding names the gap). Blameless: it names systems, rules and missing checks, never a person or a session. It cites the incident's problem id, and the next retro reads it with the problems resolved (`process/supervisor.md` §10), turning what it found into the retro's changes rather than a list of its own. Review-enforced: nothing in the kit asks for one yet.

## 5. CI and tooling

- **`L-CI-1` the forge's CI runs every gate.** On GitHub, each gate in `settings.gates` runs as a GitHub Actions job on every PR, with the same command; on another forge, its own CI does the same. The host builds and deploys; it gates nothing. `merge` still runs each gate itself unless it is `covered_by` those jobs, named in the list form (`quality.md` §2). The kit installs no workflow (`quality.md` §4): the project's CI is its own, and the Baseline goal adds it. Review-enforced.
- **TypeScript lints with ESLint and formats with Prettier,** the second of the two choices `quality.md` §2 lists, for a new project. A project already on Biome keeps it.
- **`L-FLAG-1` a feature flag is typed config, with a removal ticket.** A flag is a boolean key in the config module (`L-SEC-3`) named `feature_<x>`, and the line that declares it names the ticket that removes it. No flag vendor. Gate: a grep over the config module that fails when a line declaring a `feature_` key carries no ticket id (lint gate).

## Gates
