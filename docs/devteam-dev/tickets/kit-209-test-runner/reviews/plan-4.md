It isn't in `killed` (ppid changed), and it isn't in `unstopped` (it shows `T`). The common real cause isn't pid reuse. It is reparenting: B is seen as A's child, then A exits before its SIGSTOP lands, and B is reparented to init or a subreaper before B's stop. B is then left stopped forever, with no line in the output. It still holds whatever it held, such as a port-block lock whose pid is alive, so later runs see that block as taken. The race is rare, but the outcome changes from "killed" (pass 3) to "a silent stopped orphan". **Fix:** report these pids too, for example as `reparented: <pid>` in `unstopped` or in a separate list, so a leak is visible. Optionally kill one when its recorded parent is now absent or `Z` in the final snapshot, since a `T` pid with a dead former parent is far likelier to be the reparented child than a reused pid that someone else stopped. Extend the scripted ppid-changed case to assert that it is reported. | |
