- stopTree. Every signal goes to the root (the runner's own child, which the runner hasn't reaped, because the walk never runs once `exit` has fired, and libuv reaps and emits `exit` together) or to a pid whose snapshot ppid is a pid this walk stopped. SIGKILL needs `T` in the final snapshot under the recorded parent, or orphaned from an exited one. The only way it could signal a process outside the tree is pid reuse inside the walk's few seconds, and there the code goes the safe way: it doesn't SIGCONT or kill a pid that moved under a live parent. What the walk stopped and didn't kill is resumed. It is left stopped only in that reuse case, or if `signal` throws an unexpected errno partway, which `cleanup`'s catch can't resume. Kill order is reverse stop order. The root's group is orphaned from the start (setsid), so killing doesn't trigger the kernel's SIGHUP/SIGCONT to it.
- freeLocks and cleanupAfter. freeLocks only removes a lock whose owner is in `entry.killed` and is gone or a zombie. It runs only after a walk. A live owner, EPERM included, is never freed. The read-then-rm race needs a third process to expire the same lock (an hour old) in between, which I judged negligible.
- tmux. The runner calls only `<real tmux> -S <socket> kill-server`, on sockets whose real path is under the scratch folder, found by a walk that doesn't follow symlinks. The shim's refusal matches lib/kit.mjs's. The only leak I found is the inherited TMUX (F3).
- Exit codes. Watchdog, interrupt (128+n, which wins over the summary's 1), spawn error, non-zero exit and signal all fail the run. An empty shard or group exits 0 with `no files`, per the spec.
