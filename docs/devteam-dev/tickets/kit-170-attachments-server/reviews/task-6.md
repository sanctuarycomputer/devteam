What I checked:
- **Pane injection.** A pasted path is `attachedFiles`' realpath, and `droppedFileProblem` makes it exactly `<realRoot>/<UPLOAD_FOLDER>/<safeUploadName(name)>`, so no ESC, CR or LF can reach the paste through the file part of the path. `dropPaste` shell-quotes anything else. Only paths are pasted: the recorded `name` never reaches the pane. The paste goes in on stdin, never in argv. The buffer is named `devteam-drop-<pid>-<seq>`, which is unique per process. `-d` deletes the buffer once pasted, and `delete-buffer` deletes it if `paste-buffer` fails. `load-buffer` goes through `sh('tmux', …)`, whose opts spread keeps `timeout: TMUX_TIMEOUT_MS`. The other calls use `tmux()`, which goes through the same `sh`.
- **No files.** `typeNow`'s `!files` branch is the old expression. `holdLine` writes the same JSON when `paste` is null. `flushHeld` passes null. The queue's objects are read only by `deliverNudges`. The other `typeNow` callers (launch and restart) pass no paste.
- **flushHeld P10.** The guard requires a non-empty array of strings. Anything else is typed as the line alone.
- **dropSpace.** The kit's copy of the gateway's `dropSpace` adds a space when any path isn't an image. It is applied after the paste, as in the terminal drop. B8 checks both the png+pdf case and the png-only case.
- **T5-1.** `threadLineProblems` refuses `files` on any turn whose `by` isn't `owner`, which covers the supervisor's turns and any agent's. `checkLine` refuses `files` on a question line with channel chat or thread, which covers from-chat and from-turn. Every owner line has a channel, and the owner's own answer has neither of those two, so it passes. The test shows the owner's own turn with files passes. A defaulted answer (the supervisor's) was already refused by the authority list. Review-result and decline answers are the owner's own acts, and the CLI refuses `--files` on them. The log still allows files on those two, which matches §6's "the owner's own answer". No legitimate line is refused.
- **T5-2 zero-width (U+200B–200D, U+FEFF).** These don't reorder text. The names never reach the pane. The supervisor reads a name only as quoted data in the log. A zero-width character could at most make the owner's own file's name look identical to a different spelling on the owner's own card. Not worth a finding.
- **A paste that fails midway.** It returns false, and `recordSent` isn't called, so there is no rescue for a half-typed line. `flushHeld` keeps the record, and a later flush retypes the line after the leftover text. This is the same failure class as today's `send-keys -l` succeeding and then `Enter` failing.
