What I checked and found sound. I read cmdMerge (devteam.mjs L4937-5215), `gateAdditions`, `newGateProblem`, `GATE_ADD_FIELDS`, `OWNER_SETTINGS`, `linkOwnerChanges` and the repo-link `ownerClass`, plus `loadSettings`. The spec's account of today's merge is accurate: the first read and its normalisation, the `ignored_checks` skip, gates only for ticket and plan PRs when nothing has failed, `paths` applicability, ratchet re-run at the base, and `--match-head-commit`. One small omission: it leaves out the separate run of a chore's own added gates (`gateAdds`). The ownership claims hold. Adding `covered_by` to an existing gate makes `gateAdditions` return "it changes &lt;gate&gt;" (byte comparison, L67-68), so the owner's `gate-change` answer is needed. A new chore gate with `covered_by` is refused by `newGateProblem` (L667-668). A repo link's `gates` change is `gate-change` (`REPO_GATE_KEYS`, L877). A plan or ticket PR can't add a gate at all without the owner. An owner's standing `gate-change` rule (owner_rules) would also approve `covered_by`, which is the owner's own choice; the D3 test should run without such a rule. Appending to the act's `what` keeps `mergedAtSha` (`startsWith`, L15814) and the `^merged ticket/(\S+) ` parser (L9467) working. The head-moved check and the decision to write no `gate` line are sound, and so is the list form's every-entry-SUCCESS rule, including several entries with one name.
