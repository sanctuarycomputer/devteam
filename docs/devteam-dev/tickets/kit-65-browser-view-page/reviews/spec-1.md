| F1 | Important | done-when 2 ("each send one contract message"); spec §Input table | spec.md §Acceptance checks 2 vs §Input from the owner | The check says a click, a wheel and a paste "each make the server receive exactly one message", but the spec's own rules make that false. (a) Paste: the table sends `key {type:"down"}` and `key {type:"up"}` for "a modifier", so Ctrl+V as CDP drives it (test/lib/chrome.mjs `hold('Control', true)`, then V with modifiers 2, then Control up) reaches the server as `key down Control`, `paste`, `key up Control`: three messages. "Ctrl+V and Cmd+V send no key message" only covers the V. (b) Click: `clickAt` sends `mouseMoved` before the press, and the page sends a `move` for a move without a button held, so the server gets `move` and then `click`. A wheel at a new point can do the same. So the check can't pass as written, or a worker makes it pass by quietly changing the behaviour, for example by not sending bare modifiers, which the fixture's `Shift` down/up says the page does send. The spec has to say which. Either the check counts only the message of that kind and asserts that no `key` with key `v`/`V` is sent and nothing else arrives besides modifier and move messages, or the page holds back bare Ctrl/Meta downs until it knows the chord isn't a paste. Whichever is chosen, the check has to pin it. | |
| F2 | Important | quality.md §3 severity ("missing test with a plausible failure path"); spec §Input "Nothing is queued"; design §Security and PII ("never logs, stores or echoes") | spec.md §Input from the owner, last paragraph; §Acceptance checks | The page's own security claims have no acceptance check: input is dropped, not buffered, while the socket isn't open; nothing typed or pasted goes to the console, to storage or into the DOM. A page that queues input until reconnect, which is the natural thing to write if you want "reliable" input, passes every listed check. Yet it replays a password typed during a drop into whatever page is up later, which is exactly the failure the spec names. Add a check: drop the socket, type a marker string and paste one while it is down, then let the page reconnect. The new socket receives none of the marker. `Runtime.consoleAPICalled` never carries it, `localStorage`/`sessionStorage`/`indexedDB` stay empty, and `document.documentElement.outerHTML` doesn't contain it. | |
| F3 | Minor | spec §Acceptance checks 2 ("CDP clipboard write") | spec.md §Acceptance checks 2; §Input table, paste row | CDP has no clipboard-write command, so the mechanism the real-paste check rests on is unnamed. The spec should name a mechanism that works in `--headless=new`, so that a worker doesn't fall back to dispatching a synthetic `ClipboardEvent`, which proves nothing. For example: `Browser.grantPermissions` for clipboard read/write on the page's origin, then `Runtime.evaluate` of `navigator.clipboard.writeText(...)` with `userGesture: true`, then a real Ctrl+V through `Input.dispatchKeyEvent`; the page reads `clipboardData.getData('text/plain')`. Also, "the context menu" isn't a paste route on a non-editable canvas, because Chrome offers no Paste there. The spec also doesn't say that `contextmenu` on the canvas is prevented, so a right-click both goes to the remote and opens the viewer's own menu. | |
| F4 | Minor | spec §Input table, printable-key row; P2 (every instance) | spec.md §Input from the owner | "A printable key (one character, no Ctrl or Meta)": on Windows, AltGr sets `ctrlKey` and `altKey`, so `@`, `€`, `{` and so on, on German, French and Polish layouts and many others, fall into the "Ctrl chord" row and go as `down`/`up` with no `text`. An email or password containing one can't be typed. Treat `getModifierState('AltGraph')` (or ctrl+alt with a one-character `key`) as printable. | |
| F5 | Minor | spec §Input table (drag, keys); contract `mouse.button` | spec.md §Input from the owner | Pointer details that a worker will get wrong or have to invent. (a) The spec doesn't say what `button` the `move`s during a drag carry. CDP needs the pressed button for a drag to select text or move a slider, so state that they carry the press's button. (b) A drag released outside the canvas never sends `up`, which leaves the remote button down. Say to use pointer capture. (c) A `move` throttled to the animation frame must not be sent after the `up` or `click` that ended the drag. Flush it or drop it. (d) Only Tab and Backspace have their default prevented, so Space, the arrows and PageUp/PageDown on the focused canvas also scroll the viewer page while the owner types. (e) "a press and release at one point" needs a stated tolerance, and `clicks` should come from `event.detail` so a double click reaches the remote. | |
| F6 | Minor | contract `paste.text` maxLength 10000 (UTF-16 length, as check.mjs counts it) | spec.md §Input table, paste row | Splitting into 10 000-character pieces can cut a surrogate pair, such as an emoji in a passphrase, across two messages, which sends lone surrogates. Split on code-point boundaries, or at 9 999 when the cut would land inside a pair. Nothing bounds the number of pieces either: a 10 MB clipboard becomes 1 000 messages. A cap would do, for example refusing a paste over some size with a line under the bar. | |
| F7 | Minor | contract `wheel.dx/dy` (±100000), `nav.url`; spec §The address bar | spec.md §Input table (wheel); §The address bar; §Acceptance checks 2 and 3 | (a) Wheel deltas have no clamp to the contract's ±100000. | F8 | Minor | spec §What the page does ("scaled by CSS to the page's width"); design §4 (owner completes a login, SB-S2) | spec.md §The screen | The canvas is fitted to the page's width only, and the wheel over the canvas is prevented ("the page itself doesn't scroll"). Fit the canvas to both the width and the height available under the bar (contain), keeping the aspect. The coordinate formula still holds. | |

Values and refusals. **P1** (harness-agnostic): a static page in the owner's browser that has nothing to do with the harness. It holds on Claude Code, Codex and OpenCode alike. **P2** (nothing project-specific): it holds, apart from F4's layout gap. "this project's browser" makes sense in every instance. **P3** (decide and report): the spec decides two reversible departures from the settled mock itself: it drops "Back to the card" and adds "Show it again", each with a reason, and asks no question. That is right. **P4**: no owner question is raised. **P5** (adversarial review for authority): the page carries no Done, hand-back or answer control. Check 4 asserts that across every state, and input doesn't depend on `held`, so authority stays with the card and kit-66/kit-67. I tried to break it by looking for a control that answers or withdraws a handover and found none. `forget` is gated behind a confirm. **P6** (simple, accidental path): the page leaves origin and Host gating to kit-66 and the gateway, and says so. It doesn't defend against a same-user process opening the socket, which the design already names. **R1**: holds. Normal use of the page can't raise a rung, approve a question or write an owner line. It speaks only `$defs.view`, which has no answer message. **R2**: holds. Every owner-facing string is plain words: the refusal lines, "Reconnecting…", "When you're done, press Done on the card.", and `why` shown as text. "Only http and https addresses open here." is the most technical of them, and the owner can still act on it.
