None of those tickets touches the schema, the fixtures or `sites.mjs`, so any gap here blocks them until a new contract ticket lands. I also read `schemaErrors` (devteam.mjs:1126), log.schema.json's style, test.yml (Node 18 to 24, with the `rest` part globbing `test/*.test.mjs`), and quality.md §3. The approach is right. But the fixture site and two contract shapes don't give kit-65 and kit-67 what their done-whens need. The spec also contradicts itself on which fields carry the masked-URL pattern, and the 2FA code's format leaves kit-67's and kit-68's grep checks open to flakes. Those block. Values and refusals:

| F1 | Important | kit-67 done-when 5; spec §3 route `GET /2fa`; Contracts "Provides" | spec §3 table, `GET /2fa` row | `GET /2fa` without `pending` redirects (302) to `/login`. A successful `POST /2fa` clears `pending`. After the `variant=page` flow, the tab's last GET is `/2fa`, so the post-done GET reopen goes to `/login`. kit-67 requires "the 2FA form page after the variant that answers its POST with a page" to come back **still signed in**, with `tabs` listing only those pages. As written, the tab lands on `/login`, which shows no signed-in state, so kit-67 can't pass, and `sites.mjs` is outside its touches. Fix: specify `GET /2fa` with a live `session` and no `pending` (for example, 200 with the form page plus "Signed in as <username>"), and add that case to the contract test | fixed |
| F2 | Important | kit-65 done-when 2; Contracts (live-view messages) | spec §1 live-view table, `mouse` and `key` rows | kit-65 must show that "a real click, a wheel, typed text, Enter and a paste each send **one** contract message". Under this contract, a click can only be `mouse` down plus `mouse` up (two messages, often with moves), and Enter can only be `key` down plus up. kit-65 can't touch the schema, so its done-when can't be met literally, and its reviewer will fail it. Fix: either add compound forms (`mouse` `type: "click"` with `clicks`, and a `key` `type: "press"` that the server expands to CDP's pairs), or state the mapping in the descriptions ("a click is one down and one up") and get a supervisor ruling on kit-65's wording before kit-65 starts | fixed |
| F3 | Important | spec §1 "copied as the pattern of every URL field"; AC1 third bullet; spec §1 `nav` row | spec §1 masked URL, live-view `nav`, §4 | The spec has the test assert that "every URL field in the schema carries exactly `x-masked-url`". It also defines `from_page.nav.url` as "as the owner typed it" and unmasked. Either the test fails, or `nav` gets the mask and kit-65/66 reject any typed URL with a query value (`?q=1`), a fragment or a long path segment. The spec doesn't say how the test finds URL fields (by name `url`/`href`, by `items` of `reopened`, or by a marker). Fix: mark masked fields explicitly (for example `"x-url": "masked"`), have the test find every `url`/`href`/`reopened` field and require the marker plus the pattern on each, and exempt `nav.url` by name with its own `maxLength: 2048` | fixed |
| F4 | Important | R2 (strategy); spine Components 1 ("refuses, with a plain error page"); spine Failure modes ("The page shows the same") | spec §1 `refusal` row | The refusal body is `application/json`. On an `http:` page the owner sees raw JSON in the live view (`{"browser":1,"rule":"special-purpose",...}`), which the spec itself acknowledges ("for the owner who sees the page in the live view"). That is codespeak on an owner-facing page, and the spine asks for a plain error page. Fix: make the body an HTML page that shows `why` as its text and carries the `refusal` object machine-readably, for example in `<script type="application/json" id="devteam-refusal">`. Have the schema validate that embedded object and the test extract it. Or justify in the spec why raw JSON passes R2's check | fixed |
| F5 | Important | kit-67 done-when 5, kit-68 done-when 3 (grep that the code and password appear nowhere); quality §3 (missing test with a plausible failure path) | spec §3 "`password` and `code` are random per start" | The format of `code` isn't specified, and `inputmode=numeric` suggests a short decimal code. A random 6-digit string matches by chance inside the digit runs in the log, run/, tmux output and git (timestamps, `hhmmssmmm` ids, pids, hex SHAs), at percent-level odds per run. kit-67 and kit-68 would flake, and they can't change the site. Fix: specify a code and a password that can't collide (for example, a code of 12 or more digits with a fixed prefix the kit never writes, or alphanumeric with a marker, plus a password of 24 random characters with a marker) and state the format in the spec | fixed |
