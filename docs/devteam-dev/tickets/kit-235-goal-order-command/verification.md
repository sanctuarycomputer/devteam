Not defended, by design (spec §2, §4):
- An older kit in a mixed fleet keeps `change.order` and its hash, so log-check passes. Its Inbox card shows the change block with raw ids, though the context still gives the order in words. Its fold ignores the order lines on goals past draft and applies those on drafts unchecked, with the approved values. So until it is upgraded it may show an order applied in part, but never a value the owner didn't approve.
- The fold's plan for an answer is fixed at the answer's first line. A line written by another hand in the middle of the command's run can make the rest of that run's lines count for nothing. Lines hand-written later can only set a goal to the place the owner approved (task-2 T2-5).
- An older kit's log-check refuses the owner's `goal-order` act, because its `OWNER_ACTS` lacks the class (final-1 F2). That is the price of ruling m-20261115-094155181, and `pane-answer` landed the same way. The older-reader rule for the question's field itself holds (row 2a).
- An order question with fewer than two goals can't reach the fold or `--approved`, because the schema drops such a line on read. Their checks are defensive and untested (task-2-2 T2-2-1).
- The dashboard action's 50-id cap is read, not tested: a test would need 51 distinct live goals.

Nothing is deferred to beta.
