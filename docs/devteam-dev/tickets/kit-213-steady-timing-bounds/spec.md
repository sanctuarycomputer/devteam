# kit-213 steady timing bounds: spec

Ticket: `kit-213-steady-timing-bounds` (feature `tests-light`, serves TESTS-S3, size S, risk normal). Depends on kit-216 (`test-stress.yml`), merged at 1769b43. Touches `test/bounds.test.mjs` and `test/speed.test.mjs` only.

## Intent

The bounds in these two files must hold on a loaded machine and still catch a real slowdown. Today four of them are absolute milliseconds (or milliseconds over a reference), which a busy runner can break and which a 10x slowdown of the cheap parts would not. Each becomes a count of operations, or a ratio against a reference workload timed in the same process just before it, so load slows both sides. The design's line (D, "Steady timings"): "Where the thing being bounded is a count, the bound counts operations. Where it really is time, the bound is a ratio against a reference workload measured in the same process, just before."

Separately, the after hooks in `test/speed.test.mjs` remove folders before they stop what the test started. Node runs a test's after hooks in the order they were registered and stops at the first one that throws, so a failing removal leaves the dashboard (and its fake tmux) running. They are reordered: stops first, then removals, each step on its own.

Left as they are, and named in verification.md as hang guards, not bounds: the per-test `{ timeout: 120000 }` and `{ timeout: 600000 }`, `AbortSignal.timeout(60000)` on the answer fetch, `until()`'s default wait, and `startDashboard`'s stop wait in `test/lib/kit.mjs`. None decides pass or fail on a healthy run; each turns a hang into a failure.

Ratios use one helper: the reference and the workload run alternately, n times each, and the best time of each is kept. A burst of load hits one run, not the best of several, and steady load slows both sides alike. Margins, from the measurements above (F1-3 asked for the real figures): B1 10 is 1.8x above its worst (5.6, in a load burst) and 2.4x below its 10x ratio; B2b 4 is 4x above and (T3 measures) below; B3 4.5 is 1.7x above its worst (2.63) and 1.85x below its 10x ratio (8.3); B4 8 is 1.7x above its worst (4.8) and 2.5x below. The box runs Node 18 on 32 cores; CI runs Node 24 on 4 vCPU, so the stress run (check 2) is the real test of the margins, and any bound loosened after it has its 10x ratio measured again on CI (T4).

## Edge cases

- **The vm context's `RegExp`.** `globToRegex` calls `new RegExp(...)`, a global lookup at call time, so replacing `globalThis.RegExp` in the context with a counting `Proxy` counts compiles. Regex literals in the kit's code (`escRe`, `hasWild`) don't go through it and aren't counted. The proxy is installed through the context's own `Function` (`coverage.constructor`), so `test/lib/kit.mjs` is unchanged. One `coverage()` call compiles each glob once even with both caches off (`compileLines` builds each matcher once per call), so the count is asserted twice: after the first call, and at the end of the test, after six more `coverage()` calls and the 900 `ownersOf` asks the suggestions make (each of which calls `compileLines`). With the caches off the end count is in the thousands (F1-1).
- **The coverage reference must not share the kit's code.** If it used `pathMatches`, a slower matcher would slow both sides and the ratio would hide it. The reference's regexes are written in the test, and their match counts double as an oracle: the paths no component regex matches are exactly `cov.unowned`.
- **B3 measures CLI processes, and ranking proper is a small part of them (F1-3).** At 200 questions start-up dominates (about 100 ms of 130), and the command's own work could not be told from noise, so the fixture grows to 2,000 questions (the same shape, ten times over); its own work is then about 200 ms over a 140 ms log read. Even so, `inboxRanks` itself is a few percent of the command: made 10x slower alone it moves the ratio only from about 2.4 to 3.6. The bound is therefore on what the test's title says is bounded, the Inbox read ("ranked on every read"): `questions --json`'s read, fold and rank beyond reading the log, and the 10x check makes that 10x (`rankQuestions(questionsNow())` nine extra times, past the memo). A blow-up in ranking (the case worth catching, such as a settles walk gone quadratic) is far more than 10x of a few percent and fails it. The old bound (1,500 ms over the log read) caught neither: no 10x of 30 ms reaches it. This reading of done-when 3 for B3 goes to the supervisor with the approval request.
- **B5 when no `send-keys` has started yet at the reply.** Then the property holds trivially (the reply came before any typing), and the test's later `until()` still requires the supervisor to be told after `release`.
- **pid reuse.** Between the fake's start and the reply is a few hundred ms; reuse of that pid in that window is not a practical concern.
- **What B5 rests on (F1-6).** A kit that waited for the typing is caught by B5 only because the kit's tmux limit (`TMUX_TIMEOUT_MS`, 30 s) kills the `send-keys` before the answer fetch's 60 s abort; if that limit grew past 60 s, such a kit would fail on the fetch's AbortError instead, still a failure. A `send-keys` started more than 30 s before the reply (by the dashboard's own tick) would be dead at the reply and fail B5 falsely; in this test every `send-keys` waits for `release`, which is written only after the reply's assertions, so one ends before the reply only when tmux's 30 s limit kills it; the dashboard is up for only seconds before the fetch, so the only `send-keys` that can be 30 s old at the reply is one the reply itself waited for.
- **The search test's length.** Under 4 burners a search may take 3 s or more, so B4 stays at 3 runs of each side (as now), not 5.
