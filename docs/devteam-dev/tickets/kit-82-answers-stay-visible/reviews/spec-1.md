I read the spec against the ticket's done_when and the design (§"Answers that can't land", lines 446-450, and the `links_moved` row at 484). I then checked it against the code: `questionCard` (index.html ~1294), `reviewCard` (~1545), `reviewDecline` (~1956), `press` (~3799), `answerPress` / `cardFields` / `putBackCard` / `putBackBoxes` / `qcardOf` (~3834-3900), `render` (~4043), `drawOrHold` / `holding` (~5275-5335), `submitOf` (~4985), and the document click handler (~5527-5680, including the Post-secrets handler). On the server I read `artifactLinkNow`, `artifactLinksMoved`, `resolveQuestionLinks` and `questionsNow` in devteam.mjs (~1817-1853). For the harness I read `POLL_FAST` and the "presses" test in test/dashboard.test.mjs (~327-505), plus test/lib/chrome.mjs and test/lib/ports.mjs. Most of what the spec says about today's code is accurate. A page-side fetch stub is sound: a 409 `{error}` reaches `press()` as `Not saved: <reason>` because `out.out` is absent. The stub also leaves the real server with the question still open, so polls and forced reads keep the card drawn, and a disabled button's `click()` is a no-op, so the Shift+Enter claim holds. One gap matters, though. `answerPress` has a caller outside `questionCard`: `reviewDecline`, which is used by the review panel (`errId: 'rv'`) and by the review card's decline form. The spec's `onError` design would silently drop that caller's refusal message. There are also several smaller inaccuracies and test-strength gaps.
