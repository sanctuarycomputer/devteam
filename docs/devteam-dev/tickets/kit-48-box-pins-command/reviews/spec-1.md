On this box I ran the real `--version` outputs: `ttyd version 1.7.7-40e79c7`, `2026.10.17 linux-x64 (2026-10-21)`, `2.1.307 (Claude Code)`, `uv 0.13.7 (x86_64-unknown-linux-gnu)`, and, as `dev`, `UV_TOOL_DIR=/opt/uv/tools /usr/local/bin/uv tool list`, which gives `claude-swap v1.0.0` (exit 0; the `.lock` is 0666). With no `UV_TOOL_DIR`, the same command prints `No tools installed`.

Every done-when is restated, and the restatements are faithful and testable. The spec follows the design. Its two departures are stated and sound: it reads the release list rather than `/releases/latest`, and it hashes downloads rather than reading checksum files. The upstream shapes are right: npm `/<pkg>/latest` `.version` with `%2f`, PyPI `/pypi/<pkg>/json` `.info.version`, the GitHub releases list with `draft`, `prerelease`, `tag_name`, `assets[].name`, `browser_download_url` and `digest` (`sha256:<hex>`). The asset names match the Dockerfile's `RUN` lines. The dispatch traces correctly in both places it runs:
- In the kit's own checkout, `scriptCommon`'s root has no settings.md, and `KIT_VIEWS` + `kitsOwnRepoAt(root)` lets the command through.
- For `installed` from a non-git kit copy in a non-git cwd, `common` is null, so nothing dies. From a git cwd, the `machineWide` entry the spec adds is needed. It must test `positional[0] === 'installed'`, not only `command`.

On the real file, simulated problem 4 gives no false positives. Two things block approval. F1: the literal rule as written misses the most likely hard-coded literal, a version inside a download URL. F2: a misplaced hold is silently ignored, and the next bump then moves a tool the owner held back.

Values and refusals:
- P1 harness-agnostic: no harness is involved. Passes.
- P2 nothing project-specific: the command ships in every kit but acts only on the file it is given, and Out of scope says so. Passes.
- P3 decide and report: the calls are made and marked ("my call": `unchanged`, the ENV problem, the list over `/latest`). Passes.
- P4 owner-only asks: none asked. Passes.
- P5 adversarial for authority: no authority is touched. The release gate's checks were tried here (F1, F2, F4). Passes.
- P6 simple, names what isn't defended: `DEVTEAM_BOX_BIN` is named, and the build's own sum check backs a lying API. Passes.
- R1 no self-widening: nothing writes log or owner lines. Passes.
- R2 plain owner-facing words: the output is for the supervisor and CI, and the error lines name the fix. Passes.

| F1 | Important | done-when 2 ("a tool's version left as a literal outside its ARG"); design kit-48 verify ("No tool's version or sum appears as a literal outside its ARG"); the Dockerfile's own comment ("no version or sum is written anywhere else in this file") | spec, verify problem 4 ("a whole token: not inside a longer run of `[\w.]`; the version is also searched without its leading `v`") | The `[\w.]` boundary treats `_`, letters and `v` as part of the token. So the hard-coded URL `.../download/v2.104.0/gh_2.104.0_linux_amd64.tar.gz` passes verify for gh's bare pin `2.104.0`: `v2.104.0` is preceded by `v`, `gh_2.104.0_linux` by `_`. A bare pin is never searched with a `v` in front either. That is the literal most likely to be left behind (someone inlines a URL while debugging the `RUN`), and it is exactly what makes a bump not take effect, while the gate meant to catch it says ok. Bound the version on digits and dots only, e.g. `(?<![\d.])<ver-without-v>(?!\.?\d)`, and bound sums on hex (`(?<![0-9a-fA-F])<sum>(?![0-9a-fA-F])`). I ran that rule on the real Dockerfile: no hits. Make the done-when-2 case a URL-embedded literal (`gh_<ver>_linux` or `/v<ver>/`), not a free-standing one. | fixed: versions bounded on digits and dots, sums on hex; the done-when-2 case is gh's URL |
