I also read the design bullets (450-451, 471, 484) and the helpers in test/lib/kit.mjs and test/dashboard.test.mjs. The change itself is right and small. One reason function that takes resolved links, the field riding the `questions()` memo, and the finding beside `question-unrated` together meet all three done-whens. The design asks for nothing more. The refusal-text claim holds: an owner `answer <qid> Yes` gets past `ownerWriter`, `openQuestion`, the sensor check and `--seen`, then dies at 5743 with exactly `devteam: <qid> links the artifact moved-mock, which changed since it was asked; ask again about the page as it is now`. The read-count method also works. A `--import` module that patches `fs.readdirSync` on the default `node:fs` export is seen by devteam.mjs, which uses `import fs from 'node:fs'`; I checked this with a snippet. `NODE_OPTIONS` reaches the `dashboard-data` child, because `ownerEnv` spreads `process.env`. `diskEntries` calls `readdirSync(path.join(dir, ''))`, a path ending `/artifacts/<slug>`, and no cache skips that readdir: `oidCache` caches only blob hashes, and `gitReadCache` covers git calls in one process. The baseline is sound and stable: before any question is asked, `dashboardData`'s Library (`allArtifacts` → `draftArtifacts`) reads each draft folder once per run, and no main tree is read through readdir. After both questions are asked, the expected count is 2 per slug. A second resolution, such as calling `artifactLinksMoved(v)` without `now` or calling it again in `collectMetrics`, makes it 3, so the check catches a second resolution. No other code in `dashboard-data` calls `artifactLinkNow`, `artifactLinksMoved` or `resolveQuestionLinks`. The test as written still has two problems that make the count and the data unreliable: other processes add lines to the counter file, and a request can be served the previous run's data.

| F1 | Important | A check must fail only when the behaviour is missing (quality.md §3) | Acceptance check 1, the counter | Every process the dashboard starts inherits `NODE_OPTIONS`, so `dashboard-data` is not the only one writing to the counter file.
