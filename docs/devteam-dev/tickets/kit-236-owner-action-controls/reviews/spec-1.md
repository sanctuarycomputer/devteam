I ran the spec's setup in a throwaway bare project with the real CLI. `knowledge add` makes a candidate. The supervisor's `knowledge set --status accepted|retired` works. `--for-owner --plain` works. `goal decide <g> let-go --owner` works with no role, and is refused under DEVTEAM_ROLE=supervisor. `ask --kind owner-action` accepts `--recommendation`, `--evidence` with k-/g- ids, and k-/g- ids in `--context` (with a warning only). `dashboard-data` carries `evidence`, `asked_at`, knowledge `updates[]` and every goal's status. So the setup is possible as written. Values and refusals: R1 holds, because every new control posts only on the owner's own click, through the existing owner actions. R2 is at risk for one case (F3).

The central gap is which records a card counts. The spec includes `q.goal` and `q.evidence`, and Done waits on every record it counts. That blocks Done on ordinary owner-actions that merely serve a goal or cite a rule. There are also three mechanics the spec assumes but the code doesn't provide: the thread copy's redraw, a confirm that survives a poll, and a redraw when a peek lands.
