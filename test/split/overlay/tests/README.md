# The tests' area (kit-893)

In the tree the kit's tests read the CLI's and the gateway's source through one helper each, and a test may differ from main only in how it finds its source (`cutover-tree@1`, Tests in the tree and What a test change may do).

- `rules.mjs`
  - `cli-source`: writes `test/lib/cli-source.mjs`. Its `cliSource()` returns the CLI's source as the single file had it, read from the tree's modules when called: the shebang, the header, the import lines as written, then every module's body in the manifest's order, each imports region and each `export ` the split added taken off. On a split with no other area it is `devteam.mjs` byte for byte; where an area changed a declaration (load-time's `init()`), it shows the tree's text. It refuses, writing nothing, when the CLI as the rules see it has no import statements, or when the split makes no module of it.
  - `test-reads`: in every test file, each node:fs read goes through the helper, and nothing is refused:
    - `fs.readFileSync(…)` becomes `cliRead(fs.readFileSync, fs, …)`, an imported `readFileSync(…)` becomes `cliRead(readFileSync, undefined, …)`; `fs.promises.readFile`, a `node:fs/promises` module's `readFile` and an imported `readFile` become `cliReadAsync(…)`; the callback `fs.readFile(…)` becomes `cliReadCallback(…)`; and a read function handed on as a value (`readFile: fs.promises.readFile`) becomes `cliReader(…)` or `cliReaderAsync(…)`. Only the callee changes: the arguments stay as written.
    - When the test runs, the helper looks at the path (a string, resolved from the working directory, a `file:` URL or a Buffer): a read of the tree's `docs/devteam/scripts/devteam.mjs` gets `cliSource()`, as a string with an encoding, else a Buffer; any other read is the function's own. So a path's form (a join, a URL, a helper's parameter, a path imported from a fixture) is not the rule's concern.
    - Left as written: a member of another object (`x.fs.readFileSync`), an object key, a string, a comment, a template's text, an assignment to `fs.readFileSync` and a comparison. A file with no node:fs import is unchanged.
    - Beside the gateway's area, each read of `cloud/gateway.mjs`'s text first becomes `gatewaySource()` (`rewireGatewayReads`, kit-894's, moved here unchanged; it still refuses a read of the gateway's text it can't place). Without the gateway's helper those reads are left.
  - The files it reads: every `.mjs` under `test/` (the fixtures' helpers too) but `test/split/`, `test/split-*`, the two helpers, and any file another area of the overlay writes whole from its `files/` (package-release's `test/release/package-check.mjs`): that file is the other area's, and two areas that change one file conflict, which leaves both out. The gateway's rewrite keeps kit-894's set, which leaves `test/fixtures/` out.
- `files/test/cli-modules.test.mjs`: the rules test, checking `cli-modules@1` on the tree's `lib/`: every module imported alone loads and prints nothing (M1); `import.meta.url` in code only in `state` and `settings` (M2); every imports region as the modules' declarations make it (M3); no module over 2,000 lines (M4); no lib module imports the entry or the shim (M5).
- `finding.mjs` (not the split's: its loader lists it as ignored): `sameBeyondFinding(sourceText, treeText, file)`, the test-change check the parity run calls. It is true only when the tree's text is exactly what this area makes of main's: the rule's two rewrites, then this area's patch of that file (`patches/<basename>.patch` naming `b/<file>`), if any. There is no patch today.

`test/split-tests-rewire.test.mjs` checks all of it; `test/split-gateway.test.mjs` checks the gateway's reads beside the gateway's area alone.
